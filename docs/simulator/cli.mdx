The verb tree separates what is being acted on from what is done to it:
`spec` works on documents, `run` / `queue` / `rerun` on attempts,
`recording` on sealed evidence, `driver` and `lock` on the build.

Every verb prints a human line by default and one JSON record per result
under `--json`.

## spec

| Verb | Does |
|---|---|
| `spec check <spec>` | decodes and materializes; reports nothing else |
| `spec show <spec>` | prints the materialized spec plus where each field came from |
| `spec to-ts <spec>` | prints the spec as a typed TypeScript literal |
| `spec from-bundle <bundle...>` | splits bundles into bare RunSpecs (`--out <dir>`) |

`spec show` reports each field's origin — `user`, `default`, or
`profile` — so a value you did not write is visible as a default rather
than mistaken for a choice.

`spec to-ts` and `spec from-bundle` are the same kind of thing: total
transforms between two encodings of one spec.

## run and rerun

```bash
moltzap-testbed run my-run.yaml            # one spec
moltzap-testbed run a.yaml b.yaml c.yaml   # several
moltzap-testbed run specs/                 # a directory
```

Fan-out over the specs you name, never a matrix. Each gets its own
recording identity, its own attempt, and its own `--json` record; the
process exits with the worst of theirs. Every spec is materialized before
the first one launches.

`rerun <recording>` starts a new attempt under the same identity, from
the spec the manifest persisted — so a rerun cannot drift onto an edited
document.

## queue

| Verb | Does |
|---|---|
| `queue submit <spec>` | materializes, enqueues, and drains |
| `queue status <attemptId>` | prints one attempt's record |
| `queue cancel <attemptId>` | requests cancellation |
| `queue retry <attemptId>` | new attempt from a terminal one |
| `queue work` | drains this process's queue |

<Note>
The v0 queue lives in one process, so each verb builds the queue, acts,
and tears it down. Attempt state does not outlive the invocation. The
verbs are shaped so a durable queue behind the same seam changes nothing
here.
</Note>

`submit` materializes first, so a config-time rejection surfaces at
submission and never enqueues.

## recording

| Verb | Does |
|---|---|
| `recording show <dir>` | identity, outcome, and counts |
| `recording check <dir>` | verifies sealed and decodable; prints the outcome |
| `recording events <dir>` | the event timeline as NDJSON |

`recording check` takes `--content-version <key>` and
`--require-completed`, which add the two grading-convention refusals
(exit 13 and 14) to the three integrity ones. See
[Grading](/simulator/grading).

## driver, lock, demo

`driver check` lists registered drivers with their declared config
schemas — the same schemas materialization validates against, so the
documentation cannot drift from what a config must satisfy.

`lock` prints the pins every recording's manifest carries; `lock check`
re-reads them, so a build whose pins moved is caught before it produces
recordings claiming provenance it no longer has.

`demo` runs the no-keys fault-theater fixture.

## Exit codes

| Code | Meaning |
|---|---|
| `0` | success |
| `1` | a failure the mapping does not name |
| `2` | config-time or projection-time rejection; nothing ran |
| `3` | the run failed and sealed a recording of the failure |
| `4` | no recording exists |
| `5` | a recording exists but the seal path failed |
| `10` | not sealed, or sealed bytes changed afterwards |
| `11` | recording schema version mismatch |
| `12` | a recording file failed to decode |
| `13` | content-key mismatch |
| `14` | the run did not complete |

Codes key on stable error tags, never on messages, so a script can branch
on what happened without parsing prose.

<Note>
`sweep preview` is not in v0. Sweep orchestration — matrix enumeration,
axis-derived naming, verdict aggregation — stays outside the instrument;
`run` fans out over specs you give it and nothing more.
</Note>
