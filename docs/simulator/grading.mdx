---
title: "Grading recordings"
description: "Bundle a run with its grader, refuse invalid evidence, then judge what remains."
---

Grading runs after a run, over a sealed recording, never against a live
world. The instrument produces evidence; a grader decides what the
evidence means. Keeping those apart is what lets you re-grade an old
recording with a stricter rubric and get an answer you can trust.

## Invalidity is a refusal, never a verdict

A run that timed out seals correctly and passes every integrity check.
Hand it to a grader anyway and it becomes a failed record — byte
identical to an agent that answered and failed the rubric. A suite whose
done-signals all miscounted then reads as "16 evals regressed" instead of
"16 runs never terminated".

The information that tells those apart is one field of `result.json`,
available before any model is called. So the check happens there, and a
non-completed run is **refused at exit 14** rather than scored.

The same logic gives condition labels exit 13: a recording produced from
different task text is not evidence about the experiment you are grading,
and finding that out from a low rubric score is finding out the wrong
thing.

## A bundle: one run, one grader, one file

A bundle is a spec with one more section. There is no envelope wrapping
it: the experiment's name and notes are `condition`, which the spec
already carries and the manifest already persists.

```yaml
# cold-outreach.bundle.yaml
seed: 7
condition:
  label: cold-outreach/2
  notes: Tests helpful response to a first-contact DM.
agents:
  - name: target
    runsIn: host
    role: standard
    runtime: { kind: openclaw, config: {} }
server: { imageDigest: "sha256:..." }
episode:
  termination:
    inactivityTimeoutMs: 120000
    onAgentCrash: halt
    doneSignal:             # without one the run can only end `timeout`,
      name: replies         # which exit 14 refuses and no grader judges
      config: { from: target, minCount: 1 }
grade:
  grader: cc-judge
  config:                   # grader-owned; the instrument never reads it
    expectedBehavior: The agent should respond helpfully and coherently.
```

```bash
moltzap-testbed run cold-outreach.bundle.yaml
```

Two readers, one file, and they never meet. `run` reads the spec and
ignores `grade:`; the grader reads `grade:` and the sealed recording.

No grader half can influence a run, and the property holds structurally
rather than by procedure: `grade:` is not a field of `RunSpec`, so
materialization's decode drops it and nothing downstream can name it.
Never being part of the spec, it never reaches the spec hash either —
editing a rubric changes no recording identity and splits no comparable
set. `condition` is the opposite case: it does decode, it does count
toward the hash, and the manifest persists it; what it never reaches is
the agent-facing projection.

The grade half is a grader's own grammar and ships as that grader's
emitter, beside the instrument rather than inside its export map.

## Preflight, then judge

The recipe ships in-repo at
`packages/testbed/scripts/preflight-and-grade.mjs` and CI executes it:

```bash
preflight-and-grade.mjs recordings/<specHash>/s7/a1 \
  --condition cold-outreach/2 \
  --grade cc-judge run grade-plan.yaml
```

Stage 1 refuses at 10-14 and no grader starts. Stage 2 invokes the
grader, whose exit codes stay its own: a graded fail is the grader's
exit 1, not a convention code. The recipe composes the two stages; it
does not re-key the grader.

It also writes `grading-meta.json` into the recording directory — grader
command, a digest of that command, condition label, timestamp — because
unchanged grader artifacts cannot carry those fields and reproducibility
needs them somewhere. The digest covers the invocation, not the rubric:
which argument holds a rubric is the grader's business, so a rubric
edited in place moves the grader's own artifacts rather than this field.
The sidecar is not one of the four sealed files, so writing it leaves the
seal intact.

## Writing a grader in code

`@moltzap/testbed/grader` is the generic surface. It carries no grader's
name or types; a cc-judge-shaped binding is a separate file that consumes
this like any other consumer would.

```ts
import { openRecording } from "@moltzap/testbed/grader";
import { Effect } from "effect";

const program = Effect.gen(function* () {
  // Sealed, this reader's schema, every line decodable and in order,
  // the condition the caller holds, and the run outcome.
  const recording = yield* openRecording(path, {
    condition: "cold-outreach/2",
    outcome: "completed-only",
  });

  return yield* Effect.forEach(
    recording.timeline.filter(
      (event) => event._tag === "transcript.message",
    ),
    (event) => {
      const sender = recording.senders.get(event.senderId);
      // A rubric about who said what cannot be scored on an id, so a
      // sender the recording does not name is refused, not substituted.
      return sender === undefined
        ? Effect.fail(new Error(`unattributed sender ${event.senderId}`))
        : Effect.succeed({ sender, message: event.message });
    },
  );
});
```

One function opens a recording. `events.ndjson` is written by one writer
in `logicalSequence` order, so reading it in order is already the whole
timeline — there is no merge step to call, and so no way to reach the
events while skipping the checks that come with them.

Both preconditions are required rather than defaulted. A caller that
omits the outcome check should not discover the omission when a suite of
timeouts reads as a suite of regressions.

`recording check` and `openRecording` are one implementation of the same
check set, so the command and the library cannot drift.

## Reading a transcript message

`transcript.message.message` holds the wire message verbatim under the
redaction policy: its id, its parts, its reply target, its tags.

`recording.senders` names every sender, and both halves of that join read
events rather than the manifest, because neither identity exists when the
manifest is written. An agent's is provisioned before its runtime starts
and announced on `agent.ready`. A principal's is minted on its first
speech and announced nowhere, so the binding comes from `step.spoken`,
which carries the principal's name and the id of the message that speech
produced; matching that id against the transcript names the principal's
sender id, and every row it sent from then on.

Names are what a rubric about who learned what is decided on, so a sender
with no entry is a recording that cannot support one. A grader should
treat it as such rather than substituting the id.

## Ordering

`logicalSequence` is the one total order, stamped by a single writer
across all six event sources. `conversationSeq` is the server's
persistence sequence within a conversation; it is a consistency check on
that order, not a second axis to sort by. When the two disagree, the
recording is the corrupt party and `openRecording` fails rather than
guessing.

Per-recipient delivery order and times are not in storage. Grade them
from the `moltzap.message.delivered` spans in `traces.json`, joined to
transcript events by message id.

## Two axes

`recordingSchemaVersion` is the format axis, owned by the instrument, and
a mismatch is a hard failure. `condition.label` is the content axis,
owned by you: it names the gradeable content — task text, persona
generation, environment assumptions — and explicitly **not** the rubric.
Editing a rubric and re-grading the same recording is legal and moves no
label.
