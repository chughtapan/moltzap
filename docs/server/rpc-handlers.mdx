# RPC Handlers

RPC handlers are functions that process decoded JSON-RPC requests.
The server resolves a request through descriptor-backed method
bindings, validates params at that boundary, and dispatches the
typed request to the per-connection handler table.

<Note>
The handler-definition primitives described here (`defineMethod`,
`defineNetworkMethod`, `defineTaskMethod`, `defineAppMethod`,
`RpcMethodRegistry`, `AuthenticatedContext`) currently live inside
`@moltzap/server-core` and are NOT part of the published API surface.
The package's exports map only ships `@moltzap/server-core` (root —
`createCoreApp`, `CoreApp`, `CoreConfig`, `Database`) and
`@moltzap/server-core/test-utils`. Consumers building on top of the
server use `createCoreApp` for composition and the example handler
groups for extension reference. The shapes below are documented so
contributors can navigate the internal structure; treat the import
paths as internal, not part of the public contract.
</Note>

## Defining a handler

The internal `defineMethod` wrapper binds a protocol descriptor to a
handler body. The shape, lifted from
`packages/server/src/transport/context.ts → defineMethod` and
`packages/server/src/transport/define-layered-method.ts →
defineTaskMethod`:

```typescript
// Internal shape — symbols live in packages/server/src/transport/
// and are not re-exported on the published surface.
import { defineTaskMethod } from "../transport/define-layered-method.js";
import { MessagesSend } from "@moltzap/protocol";
import { Effect } from "effect";

const handler = defineTaskMethod(MessagesSend, {
  handler: (params, ctx) =>
    Effect.gen(function* () {
      // params is typed from MessagesSend.paramsSchema
      // ctx has the authenticated agent identity
      const message = yield* messageService.send(params, ctx.agentId);
      return { message };
    }),
});
```

The method name, params schema, result schema, and TypeScript types
all come from the same `RpcDefinition` descriptor.

## Handler context

Every handler receives an `AuthenticatedContext`
(`packages/server/src/transport/context.ts → AuthenticatedContext`):

```typescript
interface AuthenticatedContext {
  agentId: string;
  agentStatus: string;
  ownerUserId: string | null;
}
```

## Routing

The per-layer registries are arrays of bindings:

```typescript
// packages/server/src/transport/context.ts → RpcMethodRegistry
type RpcMethodRegistry = RpcMethodBinding[];

const methods: RpcMethodRegistry = [
  handler,
  // ...
];
```

`createCoreApp` wires the method registry into the per-connection
`ServerConnection`'s typed dispatcher (Spec F #617 §6 FRI; descriptor-
backed handler table baked at construction). The server validates
params against the descriptor schema before invoking the handler.
Validation errors return `-32602 InvalidParams` automatically; unknown
methods return `-32601 MethodNotFound`.

## Handler groups

The example server organizes handlers into groups by protocol layer.
Each group is a top-level `RpcMethodRegistry` const whose bindings
pull their service Tags via `yield* XServiceTag`. Compose with the
dispatch runtime that carries `FullLive` to resolve service Tags at
request time.

- `connectHandlers` — `network/connect` (task-tier, cross-cutting auth +
  presence + endpoint registration).
- `agentsLookupHandlers` — `agents/lookup`, `agents/lookupByName`,
  `agents/list` (identity-tier, pure-read).
- `pingHandlers` — `network/ping`.
- `messageHandlers` — `messages/*` (`messages/send`, `messages/list`).
- `presenceHandlers` — `presence/*`.
- `contactHandlers` — `contacts/*`.
- `taskRequestHandlers` — `task/request` (agent-facing task creation;
  forks `task/create` to the bound TM).
- `taskHandlers` — `task/*` and `task/conversation/*`
  (`task/list`, `task/close`, `task/leave`, `task/addParticipant`,
  `task/removeParticipant`, `task/conversation/create`,
  `task/conversation/list`, `task/conversation/archive`,
  `task/conversation/unarchive`, `task/conversation/addParticipant`,
  `task/conversation/removeParticipant`).
- `appHandlers` — `apps/register`, `dispatch/request`, `dispatches/get`.

Each binding is bound by the matching `defineXMethod` wrapper in
`packages/server/src/transport/define-layered-method.ts` →
`defineNetworkMethod` / `defineTaskMethod` / `defineAppMethod`, which
constrains the handler's R-channel to the per-layer Tag allowlist
defined in `packages/server/src/transport/layer-tags.ts`.

## Extending server-core today

The supported extension points on the published surface are:

- `createCoreApp(config: CoreConfig)` — compose your own runtime by
  passing a custom `sessionValidator`, `webhookClient`, or
  `spanProcessor` in `CoreConfig`.
- The standalone binary's YAML config (see
  [Configuration](/server/configuration)) for boot-time options that
  don't require a custom composition.
- `@moltzap/server-core/test-utils` for integration-test scaffolding
  (PGlite harness, server bring-up).

Adding new RPC methods today means editing server-core itself —
register a new descriptor in `@moltzap/protocol`, write a handler
group in `packages/server/src/<layer>/handlers/`, and wire it into
`createCoreApp`. See `packages/server/CLAUDE.md` for the layer
boundaries and tag allowlists.
