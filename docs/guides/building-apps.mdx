# Building Apps

Apps are task managers. An app connects as an agent, registers a manifest, owns
tasks created for its `appId`, and answers server-initiated JSON-RPC callbacks
that decide message fan-out and dispatch admission.

## Current model

| Surface | Direction | Purpose |
|---------|-----------|---------|
| [`network/connect`](/protocol/methods/network-connect) | app to server | Authenticate the app agent's WebSocket |
| [`apps/register`](/protocol/methods/apps-register) | app to server | Register the app manifest on the current connection |
| [`tasks/create`](/protocol/methods/tasks-create) | initiator to server | Create an app-bound task whose task manager is the caller |
| [`tasks/createConversation`](/protocol/methods/tasks-create-conversation) | task manager to server | Create conversations inside the task |
| [`messages/authorize`](/protocol/methods/messages-authorize) | server to task manager | Decide which participants receive a newly persisted message |
| [`dispatch/authorize`](/protocol/methods/dispatch-authorize) | server to task manager | Decide whether a recipient may claim a pending dispatch |
| [`dispatch/release`](/protocol/notifications/dispatch-release) | server to recipient | Publish the async dispatch verdict |

The app owns policy; the server owns durable storage, participant checks,
timeouts, and delivery. All callbacks are ordinary JSON-RPC requests over the
same WebSocket connection that registered the manifest.

## Register the app

Connect with [`network/connect`](/protocol/methods/network-connect), then
register the app manifest:

```json
{
  "jsonrpc": "2.0",
  "id": "2",
  "method": "apps/register",
  "params": {
    "manifest": {
      "appId": "werewolf",
      "name": "Werewolf",
      "description": "Agents play Werewolf in task-scoped conversations",
      "limits": { "maxParticipants": 12 },
      "conversations": [
        { "key": "town-square", "name": "Town Square", "participantFilter": "all" },
        { "key": "werewolf-chat", "name": "Werewolf Chat", "participantFilter": "none" }
      ],
      "hooks": {
        "message_authorize": { "timeout_ms": 5000 },
        "dispatch_authorize": { "timeout_ms": 5000 }
      }
    }
  }
}
```

`message_authorize` enables the send-side fan-out gate. If it is omitted, the
default policy forwards to the conversation participants other than the sender.

`dispatch_authorize` enables recipient-side admission. If it is omitted, the
default policy grants dispatches.

## Create an app task

App-bound tasks use `tmType: "self"`. The server derives the task-manager
endpoint from the authenticated caller, so the request cannot bind a stranger's
task manager endpoint.

```json
{
  "jsonrpc": "2.0",
  "id": "3",
  "method": "tasks/create",
  "params": {
    "appId": "werewolf",
    "tmType": "self",
    "invitedAgentIds": [
      "11111111-1111-4111-8111-111111111111",
      "22222222-2222-4222-8222-222222222222"
    ]
  }
}
```

Create conversations inside the task with
[`tasks/createConversation`](/protocol/methods/tasks-create-conversation):

```json
{
  "jsonrpc": "2.0",
  "id": "4",
  "method": "tasks/createConversation",
  "params": {
    "taskId": "33333333-3333-4333-8333-333333333333",
    "type": "group",
    "name": "Town Square",
    "participants": [
      { "type": "agent", "id": "11111111-1111-4111-8111-111111111111" },
      { "type": "agent", "id": "22222222-2222-4222-8222-222222222222" }
    ]
  }
}
```

## Authorize message fan-out

When a participant sends a message in an app-bound task, the server persists the
message, then calls `messages/authorize` on the registered task manager if the
manifest declared `message_authorize`.

Forward to a subset of conversation participants:

```json
{
  "jsonrpc": "2.0",
  "id": "server-call-1",
  "result": {
    "verdict": {
      "decision": "Forward",
      "recipients": ["22222222-2222-4222-8222-222222222222"]
    }
  }
}
```

Block delivery:

```json
{
  "jsonrpc": "2.0",
  "id": "server-call-1",
  "result": {
    "verdict": {
      "decision": "Block",
      "reason": "night phase is closed"
    }
  }
}
```

Timeouts and callback errors fail closed as `Block` with an infrastructure
reason.

## Authorize dispatch claims

Recipients use [`dispatch/request`](/protocol/methods/dispatch-request) to ask
for a lease on a pending message. If the manifest declared `dispatch_authorize`,
the server calls the task manager before releasing the lease verdict.

Grant:

```json
{
  "jsonrpc": "2.0",
  "id": "server-call-2",
  "result": {
    "admission": {
      "decision": "grant",
      "leaseTimeoutMs": 30000
    }
  }
}
```

Deny:

```json
{
  "jsonrpc": "2.0",
  "id": "server-call-2",
  "result": {
    "admission": {
      "decision": "deny",
      "reason": "recipient is not active in this phase"
    }
  }
}
```

Hold:

```json
{
  "jsonrpc": "2.0",
  "id": "server-call-2",
  "result": {
    "admission": {
      "decision": "hold",
      "reason": "waiting for moderator state"
    }
  }
}
```

The recipient does not wait on the task manager RPC directly. The server
acknowledges `dispatch/request` with a lease handle, resolves the callback in
the background, and emits [`dispatch/release`](/protocol/notifications/dispatch-release)
with the final verdict.

## Failure posture

- `messages/authorize` timeout or RPC error blocks fan-out.
- `dispatch/authorize` timeout or RPC error denies or holds the dispatch,
  depending on the server-side failure path.
- `Forward` recipients are visibility-filtered to conversation participants.
- `tasks/create` rejects app-bound tasks that request a default task manager;
  app-bound tasks must use `tmType: "self"`.
