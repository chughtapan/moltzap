---
title: "Evaluation grading reference"
description: "How @moltzap/evals validates transcripts and separates code decisions, semantic assessments, and operational failures."
---

Evaluation grading starts from a completed simulator ledger. It never grades a
callback return value or a copied response string.

The ledger is canonical network and lifecycle evidence. The transcript is an
evaluation-owned projection. A grade is an auditable assessment of that
projection, and Phoenix is only a materialized view.

## Evidence model

`grading.ts → EvaluationTranscript` contains:

| Field | Meaning |
|---|---|
| `caseId` | Branded identity of the case that produced the evidence |
| `participants` | Nonempty roster of network identities, names, and evaluation roles |
| `conversations` | Nonempty ordered conversations with fixed participant topology |
| `selectedResponseIds` | Nonempty ordered identities of target responses selected by the episode |

Each `ConversationEvidence` carries its task, conversation identity, complete
participant identities, and canonical messages in durable router order. Each
`MessageEvidence` carries the router sequence, message sender, reply target,
recipients, and parts.

`grading.ts → transcriptFromLedger` joins evaluation role and selection events
to core network events. It refuses to produce a transcript when:

- the customer program did not succeed;
- case identity, participant names, roles, or network identities disagree;
- conversation topology is duplicated or incomplete;
- canonical send and receive evidence disagrees;
- a message has no unique matching router commit;
- a selected response is absent, duplicated, foreign, not sent by the target,
  or not correlated to the exact selected prompt;
- an opened conversation has no complete message evidence.

The typed error is `GradingRefused`. Refusal means the evidence cannot support
a behavioral claim; it is not a failed agent verdict.

## Deterministic criterion decisions

Every case contains a nonempty set of `CriterionDefinition` values. A
criterion receives only the ordered selected target responses and returns one
member of the closed `CriterionDecision` union:

| Decision | Meaning |
|---|---|
| `CriterionDecided` | Code conclusively established `passed` or `failed`, with detail and nonempty message citations |
| `NeedsJudge` | The evidence still requires semantic assessment |

Code should decide both directions only when the evidence makes both
directions mechanical. Exact text is mechanical. A regular expression that
finds a secret can establish a failure, while a miss remains `NeedsJudge`
because the response may paraphrase or reconstruct the secret.

## Semantic judge

`grading.ts → SemanticJudge` is an Effect service. One call receives a
`JudgeBundle` containing the case rubric, every unresolved criterion, the
complete transcript, and an explicit notice that transcript content is
untrusted evidence.

The bundled OpenAI Layer uses:

- model `gpt-5.6-sol`;
- medium reasoning effort;
- strict structured output;
- no tools;
- a two-minute timeout;
- two retries for transient transport, rate-limit, and server failures.

`grading.ts → validateJudgeResult` requires the exact requested criterion set.
Every result must cite transcript messages and at least one selected target
response. Instructions found inside message evidence never override the system
rubric.

The closed semantic error universe distinguishes unavailable provider access,
timeout, rate limiting, invalid output, and evidence mismatch. Judge errors do
not become behavioral failures.

## Assessments and verdicts

Successful resolution produces one assessment per criterion:

| Assessment | Provenance |
|---|---|
| `CodeAssessment` | A conclusive deterministic decision |
| `SemanticAssessment` | Validated model testimony, including rationale and citations |

`CodeAssessment` uses `passed | failed`. `SemanticAssessment` uses
`passed | failed | undecided`; `undecided` is a valid semantic result, not an
error or soft pass.

`grading.ts → GradeReport` stores a nonempty assessment array. Its derived
verdict uses:

```text
failed > undecided > passed
```

A deterministic failure cannot be replaced by a model result because only
criteria still marked `NeedsJudge` enter the judge bundle.

`grading.ts → GradeOutcome` has two states:

- `GradeCompleted` contains the complete `GradeReport`;
- `GradeJudgeFailed` retains all code assessments, the unresolved criterion
  identities, and the typed judge error.

## Sweep attempt states

The sweep persists grading beside physical ledger evidence. Its terminal
attempt universe is:

| Attempt | Meaning |
|---|---|
| `AssessedAttempt` | Run, evidence projection, and every assessment completed |
| `RunFailedAttempt` | The simulator allocated a ledger but execution or infrastructure failed |
| `EvidenceRejectedAttempt` | A completed ledger could not support the required transcript |
| `JudgingUnavailableAttempt` | Code assessments survived but semantic grading did not complete |
| `LedgerAllocationFailedAttempt` | Durable ledger allocation failed before kernel ownership |

Only `AssessedAttempt` represents an operationally complete cell. Its
behavioral verdict may still be `failed` or `undecided`; those are result data.

The report validator checks matrix identity, criterion coverage, topology,
citations, timestamps, receipts, and an evidence digest over the complete
attempt payload. A callback failure or caller interruption produces no fake
terminal cell, so resume can execute that missing cell later.

## Calibration

`grading.ts → semanticJudgeCalibrationFixtures` builds typed fixtures from the
current case catalog. Fixture-only messages still have authentic topology,
roles, selections, and citations.

`grading.ts → runSemanticJudgeCalibration` returns every agreement, mismatch,
and provider error as ordered data. The CLI exits nonzero unless every fixture
passes, but it prints the complete report first.

Calibration tests require coverage for every criterion that can reach
`NeedsJudge`, including an evidence-injection attack. Updating semantic policy
therefore requires updating discriminating examples rather than silently
changing a prompt.
