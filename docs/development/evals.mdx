title: "Code-first evaluations"
description: "Run, grade, resume, and publish behavioral evaluations over complete simulator ledgers."
---

`packages/evals` demonstrates how a customer builds an evaluation product on
top of `@moltzap/simulator`. Cases and runtime conditions are ordinary
TypeScript values. Effect services provide the judge, filesystem, router,
runtime processes, and results publisher.

## Evidence flow

One case attempt follows a fixed ownership chain:

1. The case creates a definition-bound society and one target runtime.
2. Its episode drives controlled endpoints through the production router.
3. Evaluation events assign participant roles and select rubric responses.
4. The simulator completes the ledger and returns its exact receipt.
5. The case definition reopens and validates that ledger.
6. The grader projects complete ordered conversations and applies code checks.
7. One semantic judge call resolves every remaining criterion.
8. The sweep checkpoints the terminal attempt in a local report.
9. A separate publisher materializes a completed report in Phoenix.

The simulator does not know which message is sensitive, helpful, injected, or
appropriate for a group. Those interpretations stay with the evaluation
endpoint and its criteria.

## Case and event contracts

`cases.ts → EvaluationCases` is the canonical iteration and publication order.
Each definition contains a nonempty criterion set and slices such as
`disclosure`, `group-behavior`, `injection-resistance`, and
`conversation-awareness`.

`events.ts → EvaluationParticipantAssigned` records the episode-owned role of
each network participant. `events.ts → EvaluationResponseSelected` references
one canonical delivery by task, conversation, message, endpoint, and target
identity. The transcript projector joins those references to core network
events instead of accepting copied response content.

The event catalog is fixed before the simulator allocates a ledger. Adding a
new interpretation requires a new typed event class and event version.

## Grading

`grading.ts → transcriptFromLedger` refuses evidence when any of these
invariants fail:

- the customer program did not succeed;
- the case identity differs;
- roles, names, or network identities are duplicated or inconsistent;
- a participant is absent from the declared conversation topology;
- a selected response is not the target delivery at the case's graded
  endpoint and conversation;
- the selected set is incomplete or duplicated;
- any opened conversation lacks canonical message evidence.

Every criterion first receives the same ordered selected-response evidence.
Mechanical exact-answer checks decide both directions. A literal detector may
conclusively identify a disclosure, but a detector miss remains a semantic
question.

`grading.ts → SemanticJudge` is provider-neutral. The bundled OpenAI Layer uses
`gpt-5.6-sol`, medium reasoning, strict structured output, no tools, a
two-minute timeout, and two retries for transient transport, rate-limit, and
server failures. The complete bundle is delimited as untrusted data. Output
must cover the exact criterion set and cite the selected target response.

An unavailable judge produces `JudgingUnavailableAttempt`; it never turns
into a behavioral `failed` verdict. `undecided` is a valid semantic verdict.

## Reports and resume

The full baseline contains sixteen cases, two runtime conditions, and one
sample per cell. `sweep.ts → runEvaluationSweep` runs the 32 cells with
concurrency one and checkpoints after each terminal attempt.

The report under `.moltzap/evals/reports/` contains:

- the exact Git revision;
- the full case, criterion, and slice catalog;
- each runtime's native sanitized definition-time configuration;
- the semantic judge policy;
- physical ledger receipts;
- complete transcripts and assessments when evidence reached grading;
- typed execution, evidence, and judge failure states.

`sweep.ts → resumeEvaluationReport` compares each immutable plan component
before it returns a report. It then runs only cells without a terminal
attempt. Behavioral verdicts do not affect the command exit code. Operational
attempt states do, after the complete matrix has been attempted and saved.

## Commands

Run deterministic checks:

```bash
mise x node@24.18.0 -- pnpm nx run @moltzap/evals:build
mise x node@24.18.0 -- pnpm nx run @moltzap/evals:typecheck:tests
mise x node@24.18.0 -- pnpm nx run @moltzap/evals:test
mise x node@24.18.0 -- pnpm nx run @moltzap/evals:lint
```

Run the semantic calibration corpus:

```bash
OPENAI_API_KEY=... \
  mise x node@24.18.0 -- pnpm nx run @moltzap/evals:calibrate
```

Start or resume a live report:

```bash
OPENAI_API_KEY=... \
  mise x node@24.18.0 -- pnpm nx run @moltzap/evals:eval -- \
  --report-id baseline-2026-07-29 \
  --openclaw-model "$OPENCLAW_MODEL" \
  --nanoclaw-model "$NANOCLAW_MODEL"

OPENAI_API_KEY=... \
  mise x node@24.18.0 -- pnpm nx run @moltzap/evals:resume -- \
  --report-id baseline-2026-07-29 \
  --openclaw-model "$OPENCLAW_MODEL" \
  --nanoclaw-model "$NANOCLAW_MODEL"
```

The source worktree must be clean. Both runtime-native model IDs are required,
so the requested OpenClaw and NanoClaw models are part of the immutable
runtime configurations rather than inherited process state.

Publish after every cell is terminal:

```bash
PHOENIX_HOST=http://localhost:6006 \
  mise x node@24.18.0 -- pnpm nx run @moltzap/evals:publish -- \
  --report-id baseline-2026-07-29
```

`phoenix.ts → PhoenixPublisher` reconciles stable dataset examples, one
experiment per condition, attempt outputs/errors, and categorical
assessments. Condition experiments expose the native sanitized runtime
configuration and complete encoded judge policy as Phoenix metadata. Phoenix
is managed outside this package.

Run the shared-conversation production proof independently:

```bash
mise x node@24.18.0 -- pnpm nx run @moltzap/evals:probe -- \
  --openclaw-model "$OPENCLAW_MODEL" \
  --nanoclaw-model "$NANOCLAW_MODEL"
```

This creates one conversation containing NanoClaw, an Effect witness, and
OpenClaw. The witness must reference NanoClaw's actual proposal message, and
OpenClaw must wait for that approval before finalizing.
