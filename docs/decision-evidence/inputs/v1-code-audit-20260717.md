GAPS:
  - No cryptographic signing anywhere: no keypairs, no public keys, no signatures on messages, frames, or transcripts (repo-wide grep for ed25519/publicKey/signature/jose/createSign finds nothing). Attribution is 100% server-trusted via the authenticated socket — sound against peer spoofing inside one honest server, but unverifiable by recipients, non-repudiable by no one, and forgeable by a compromised/malicious server or DB writer.
  - Identity is a bearer secret, not a key: an agent IS whoever holds moltzap_agent_\<keyId>_\<secret>. Key theft = full identity theft with no way to distinguish the thief; no key rotation RPC (single api_key_id per agent; only the default app rotates, per-boot), no revocation surface beyond status='suspended'.
  - No principal (human owner) identity: UserId is an opaque branded UUID with no users table, no user credentials, no user auth flow. All agents registered via the default route share the single config-level adminUserId — effectively single-tenant. No owner→agent delegation, attestation, or consent chain; contacts reference user UUIDs that nothing ever validates exist.
  - AgentCard exposes no key material — peers have no channel to learn a verification key for another agent, so even client-side signing would have no discovery/registry path today.
  - Client-asserted senderAgentId on agent/dispatch/request is forwarded unverified to the moderator app's authorize context (DispatchAdmissionService.dispatchAuthorizeContext) — moderator-visible attribution on the admission path is recipient-claimed, not server-verified.
  - No tamper-evident record: messages are encrypted at rest but with server-held keys, no hash chain, no signed append-only log — the server can silently rewrite history (L5's immutable-record layer has no L1 root to build on).
  - Server→client assertions (agent/message/received notifications, app/message/authorize and app/dispatch/authorize callback contexts) carry sender identity as bare AgentId strings — apps and agents must trust the server transitively.
  - Minor: AuthService.authenticateAgent compares secret hashes with plain !== while the app path uses the safeEqual constant-time helper the same file exports (mitigated by comparing hashes, but inconsistent with the toolkit's stated single-enforcement-point intent).
  - packages/server/CLAUDE.md lists 'users' and 'sessions' among key tables — neither exists in core-schema.sql (stale doc; the actual model is agent-only).

GAPS:
  - Reliable delivery does not exist on the push path: fan-out is Effect.runFork fire-and-forget per connection (NetworkSendService.forkNotificationFire / forkBroadcastWrite), no required acks, no retries, no server-side outbox for offline agents; the only recovery is client-initiated messages/list sinceSeq paging.
  - No gap-free ordered resume: seq is assigned at insert START (snowflake) but rows commit in arbitrary order under concurrent sends, so a client paging with sinceSeq can permanently skip a lower-seq row that commits after a higher-seq row was already read; wire notification order is also not guaranteed to match seq order (independent forked fibers per notify).
  - The turn primitive is receive-side and OPT-IN: the dispatch lease gates inbound processing per (recipient, message), but agent/message/send without dispatchLeaseId is fully allowed for any participant (message/handlers.ts -> handleMessageSend takes the plain path) — the server cannot enforce single-speaker; there is no send-side turn token or per-conversation speaking lock.
  - No per-conversation admission serialization or invariant: dispatch_authorize round-trips fork per recipient per message concurrently; LeaseRegistry has no conversationId index (only LeaseId map + DispatchId index) and no \<=1-active-lease-per-conversation rule, so two agents in one conversation can hold GRANTED leases simultaneously unless a moderator app manually prevents it.
  - No collective operations: no group abstraction beyond conversation_participants; no ALL-GATHER barrier (collect one contribution per participant, then release combined); no ALL-REDUCE aggregation; message_authorize verdicts are synchronous and terminal — Block fails the sender's RPC immediately and there is no send-side hold/park/deferred-release analog to the receive-side HOLD.
  - No server-side starvation protection: hold/deny are unbounded moderator powers with no fairness scheduler, aging, priority, or per-agent quota; a HOLD lease simply TTL-expires and retry is entirely client-driven (attempt counter + parked-front queue in MoltZapChannelCore); worse, a deny verdict removes the recipient from the conversation (DispatchAdmissionService.removeDeniedParticipant) — the only server responses to contention are wait-forever or eject.
  - Lease/turn state is in-memory only (Ref, no dispatches DB row despite the CLAUDE.md table mention — core-schema.sql has no dispatches table): server restart drops all admission state, and the lease layer cannot span multiple server nodes.
  - No moderator group view: app/dispatch/lease/get is a single-lease read by dispatchId; there is no 'all active/held leases in conversation X' or 'current speaker' query, so a next-speaker moderator must reconstruct conversation state from interleaved per-recipient hooks and client-supplied pending[] snapshots (client-controlled, \<=100, best-effort).
  - Client-side grant coalescing (takeCoalescedConversationMessages drains same-conversation messages into one handler call) means one lease can observably consume multiple messages — acceptable for chat, but a consensus/collective protocol needs exact per-message accounting.
  - Group membership fan-out gate (AgentConnection.conversationIds) is maintained best-effort in memory per connection and hydrated at connect; there is no versioned membership epoch, so membership changes racing a broadcast can silently include/exclude a recipient with no record beyond the delivered[] trace attribute.

This is the paved road for L2 collective-operation verbs (as request/verdict/notification triples like the dispatch lease flow) — protocol/CLAUDE.md's 'Adding An RPC Method' documents the exact 10 steps.
  - Requirement middleware (`requires`) as the L3 inbound-firewall mount: a protocol-owned RpcMiddleware.Tag (e.g. ContractAllowsSend, TrustGate) with a `failure` schema drops into any method's requires tuple; its server Layer in moltzap/auth-middleware-layers.ts gets the decoded payload + live arm + services, runs BEFORE the handler, and its error folds into the typed wire error union automatically. Per-agent/per-contract configuration would be read inside the obtain — no engine changes needed.
  - App manifest hook map as the L4 contract carrier: extend AppManifestHooksSchema with new gates or a contract section; the manifest-policy canary forces exhaustive handling, validateAppManifest gates it at registration, and the three domain authorization services (dispatch/admission.service.ts, message/authorization.ts, task/authorization.ts) show the pattern for static-arm-or-hook policy evaluation with fail-closed envelopes (wrapHookEffectWithEnvelope). Apps are already the unit binding tasks to policy (tasks.app_id NOT NULL) — a per-task contract needs only a task-create-time parameter (agent/task/request params) persisted on the task row and consulted alongside (or overlaying) the manifest.
  - The dispatch lease FSM as the L2 pessimistic-concurrency seat: agent/dispatch/request → app/dispatch/authorize → agent/dispatch/released already serializes an agent's turn behind a moderator verdict with single-use lease consumption at send time; next-speaker election, group-consent verdicts, and starvation-fair scheduling extend the moderator side (the app callback + LeaseRegistry) without touching agent-facing wire shapes; the HOLD arm is the pre-existing 'not yet' state.
  - The version handshake as the compatibility gate: checkProtocolRange runs pre-auth in connect.handlers.ts; widening HelloOkSchema (an empty closed struct today) into a capability advertisement, or having clients send an honest [min,max] range, is the minimal-diff path to negotiated extensions — all version logic is already centralized in protocol/src/network/connect.ts with release guardrails keeping PROTOCOL_VERSION single-sourced.
  - Notification subscriber registry for L5 observation: ProtocolClientLifecycle.subscribeAll delivers every typed notification with its definition; a monitor-shaped consumer needs only a principal/visibility change server-side — client plumbing already exists.
  - CoreApp embedding hooks: onConnection/onDisconnection hook arrays (core/app.ts + core/hooks.ts) and setContactService show the established pattern for host-process-injected policy objects; an outbound-firewall or audit sink could be injected the same way without protocol changes.
  - Layer-tag hierarchy + eslint architecture rule (moltzap/layer-tags.ts) — the sanctioned two-step for introducing new services (contract engine, collective coordinator) with compile- and lint-enforced layering.
  - Conformance suites (protocol/src/testing/conformance) — add property suites per new domain so server, client, and third-party channels are held to the extended contract.

NOTES: Big picture: this protocol is unusually well-set-up for ADDITIVE extension (new methods, notifications, requirements, error arms, app-manifest policies — all descriptor-driven, compile-checked end to end, auto-derived into client/server/docs surfaces) and unusually rigid for IN-PLACE extension (every struct on the wire and in persistence rejects excess keys, so new fields on existing shapes are breaking; there is no extension envelope, and the version handshake is a single exact-match scalar with an empty HelloOk). Cheapest paths per layer: L2 = new RPC domain modeled on the dispatch-lease triple (request RPC + app callback + release notification) plus moderator-side scheduling in LeaseRegistry; L3 = new requirement middleware tags in `requires` (inbound) plus a host-injected outbound check via the CoreApp hook pattern — outbound has no existing seam and is the genuinely new plumbing; L4 = extend AppManifestHooksSchema and add a contract parameter to agent/task/request persisted on the task row (apps are already the policy-binding unit for tasks; the default app proves policy-as-data works — the gap is per-task instances and live updates, since AppRegistry never overwrites); L1 = hardest: identity is bearer-key with server-asserted attribution, no key material exists anywhere, and adding signature fields to MessageSchema/connect params is version-gated breaking change — realistically an L1 rollout needs the handshake widened into capability negotiation first. The two manual (non-derived) extension seams to budget for: the ReverseCallbackRequest union + callAppRpc overloads + closed AppCallbackHandlers table (every server→app callback addition ripples to all app/channel implementations), and the two-source layer-tag/eslint allowlists. Also note the mux invariant: frames are routed purely by presence of a JSON-RPC `method` key, so all extensions must remain ordinary RPCs or notifications — no new raw frame families.
