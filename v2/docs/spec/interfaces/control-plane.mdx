# Control plane

The operator face of the network: the CLI drives it, automation
drives the same RPCs. Control-plane calls never appear in a
conversation record — anything that must be ordered against message
flow is a stream entry instead (P-MEM.1).

## Operations

| RPC | Contract |
|---|---|
| `identity.register` | Binds name + principal + verification key; yields `AgentId` and credential. The registration P-ATTR.1 verifies against. |
| `conversation.create` | Mints an opaque `ConversationId` and commits the initial `MEMBERSHIP` entry at position 1 (P-MEM.1). Stranger-reach refusal is open question #2. |
| `stream.read` | The [ledger](./ledger) `read` exposed to operators and endpoint bootstrap; same contract, same P-LOG.4/5 obligations. |
| `hello` | Protocol version check at connect (below). |

Deliberately absent, with reasons:

| Absent RPC family | Why |
|---|---|
| contacts | L3 local trust data, not network objects (see [Components → Endpoint](../components)) |
| tasks | endpoint conventions (clause 2 — canonical statement in [Components → Endpoint](../components)) |
| presence, delivery status | chartered with L2 semantics (#765) |
| app registration, manifests, hooks | banned by clause 2 |

Deferred, recorded here so it is not re-derived: recovery from total
endpoint state loss (an endpoint that has forgotten which
conversations it belongs to). Whatever the answer, it is a
control-plane read over facts the network already sequences; the
minimal surface for it is a future decision.

## Versioning

The protocol version is a calendar date, matched simply; no
capability negotiation (clause 14). Layering, not negotiation, is
the compatibility mechanism ([overview](../overview)). v1's
exact-match single-scalar handshake carries forward as-is until
evidence demands otherwise.

## Wire discipline

Whether v2 keeps v1's closed-struct excess-key rejection is open
question #10. Working posture until it is bound: **strict decode at
every trust boundary** (the v1 discipline demonstrably prevented
silent drift), with evolution provided by layering rather than by
tolerated unknown fields.

## Implementation note (non-normative)

v1's descriptor-driven catalog (typed RPC definitions with schemas,
principal requirements, and derived docs) is carry-forward tooling
for authoring this surface — the catalog mechanism survives even
though most of its v1 members do not.
