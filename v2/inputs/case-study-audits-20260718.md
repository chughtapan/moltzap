## VidushiS/moltzap-propagation-bench (private pnpm project; `package.json.description` cites upstream `chughtapan/moltzap#360`). Default branch tip is a merge of `s2-experiments`. It is an external consumer of moltzap, NOT part of the monorepo. Cloned shallow to scratchpad; `node_modules` were not installed, so dependency versions below are read from `package.json`, not resolved on disk.

**Purpose:** The experiments harness for the "social-harness"/multi-agent-failure-propagation paper (a "Taxonomy of Multi-Agent Failure", per `website/taxonomy.json`). It spawns real `openclaw` LLM agents as sandboxed OS subprocesses onto a moltzap-protocol messaging network, seeds a scenario, and records what the agents say to each other. Two modes: (1) driverless propagation/attack runs (one initially-compromised agent sends a seed message; you watch it spread), and (2) auto-graded coordination experiments (meeting-scheduling with N agents, faulty/malicious behaviors). The taxonomy spans honest (distributed-liveness, concurrency, incentive-misalignment), manipulative (byzantine, machiavellian), and abusive (side-channel, agentic-viruses) agents. Scenario dirs named `s1-e1`, `s2-e1`, `s2-e2`, `s4-*`, `s8-*` are the paper's scenario/experiment matrix (the "E1-E7 style" the task references); named scenarios (`byzantine`, `starvation`, `deadlock`, `mach-gaslight`, `meeting-negotiation`, `distributed-calendar-recon`, etc.) are the taxonomy leaves.

**Structure:** TypeScript + ESM, Effect 3.21, Kysely + pg, Hono, vitest; build is plain `tsc` (root `tsconfig.json` + `bench-server/tsconfig.json`), pnpm@9, Docker Compose (postgres :43101, bench-server :13100). Top-level layout:
- `src/` — bench library (public API in `src/index.ts`). Orchestration: `fleet.ts` (`Fleet.start`), `bench.ts` (passive WS `Bench`), `run-scenario.ts` (`runOnce`/`runScenario`), `observer/db-poll.ts` (`DbPollObserver`). Scenario DSL: `params.ts` (~39KB yaml validator, `ParamsConfig`), `compile-experiment.ts` (~54KB compiler → `CompiledExperiment`/`CompiledOutcome`), `condition.ts` (condition slug), `experiment.ts` (`ExperimentConfig` + manual-JSON loader), `verdict.ts` (auto-grader), `experiment-report.ts` (EXPERIMENT.md). Plumbing: `seed.ts`, `seed-template.ts`, `workspace.ts`, `personas.ts`, `received.ts`, `skills.ts`, `topology.ts`, `credentials.ts`, `rpcs.ts`, `stacks.ts`, `db/{client,schema}.ts`, `templates/persona/{attacker,victim,relay,neutral}.md`.
- `bench-server/` — ~360 LOC minimal moltzap WS server: `src/index.ts`, `src/create-app.ts`, `src/handlers/{auth,conversations,messages,contacts}.ts`, `src/migrate.ts`, 3 vendored SQL migrations in `migrations/`.
- `vendor/runtimes/` — vendored `@moltzap/runtimes` (openclaw spawn adapter `openclaw-adapter.ts`, `fleet.ts`, `channel-plugin-install.ts`, `child-env.ts`, `sandbox-launcher.ts`, `await-agent-ready.ts`); provenance in `vendor/runtimes/README.md`.
- `runtime-plugins/bench-capture/` — observe-only openclaw plugin (ESM, no build) that prints `@@BENCH_INBOX@@ {json}` per inbound turn.
- `experiments/<name>/` — ~50 scenarios (params.yaml or manual JSON) + committed `runs/`/`received/` evidence.
- `scripts/` — `experiment.ts` (yaml driver), `play.ts`, `matrix.ts` (cartesian sweep), `clean-experiment-rows.sh`, `build-website.js`/`serve-website.js`, `proposal-completeness.ts`.
- `website/` — generated taxonomy showcase; `viewer.js` — run viewer; `patches/` — pnpm patches; `docker-compose.yml`.

**Moltzap Consumption:** Pinned deliberately to moltzap-app's DEPLOYED server line, not latest OSS (`CONTRIBUTING.md` "Pinned moltzap versions": newest `2026.504.x` "diverged the contacts surface and message shape"). Five distinct couplings:

1. `@moltzap/protocol@2026.408.0` — type + validator source of truth. Imports `ConnectParams`, `MessagesSendParams`, `ConversationsCreateParams`, `ContactsListParams`/`Add`/`Accept`, `AgentsLookupParams`, `HelloOk`, `EventFrame`, `RequestFrame`, plus runtime `validators`, `EventNames`, `eventFrame`, `ErrorCodes`, `PROTOCOL_VERSION`. Subpath import `@moltzap/protocol/phone-hash` → `hashPhone` (in `src/seed.ts`).

2. `@moltzap/client@2026.407.0` (411 also declared) — `MoltZapWsClient` (client-side embedding). CRITICAL: 407 `sendRpc(method, params)` returns `Promise<unknown>`, so `src/rpcs.ts` hand-writes typed wrappers (`contactsAdd`, `conversationsCreate`, `messagesSend`) and `src/bench.ts` manually validates the `HelloOk` shape (`readAgentIdFromHelloOk`). Patched via `patches/@moltzap__client@*.patch`.

3. `@moltzap/server-core@2026.329.0` — used two ways. (a) `bench-server/src/create-app.ts` composes a REAL server from its internals: `AuthService`, `ConversationService`, `MessageService`, `ParticipantService`, `DeliveryService`, `ConnectionManager`, `Broadcaster`, `EnvelopeEncryption`, `createDb`, `createRpcRouter`, `defineMethod`, `RpcError`, `logger`, `seedInitialKek`, types `AuthenticatedContext`/`Db`/`RpcMethodRegistry`. (b) `src/seed.ts` uses `generateApiKey()`; `src/observer/db-poll.ts` uses `EnvelopeEncryption` + standalone `deserializePayload`/`unwrapKey` to decrypt the `messages` table (KEK→DEK→envelope).

4. `@moltzap/openclaw-channel@2026.411.0` — NOT imported as a module; its `dist/` is copied onto disk into every agent's `<stateDir>/extensions/openclaw-channel/` by `vendor/runtimes/channel-plugin-install.ts` so the openclaw runtime loads it as a plugin (with `@moltzap/protocol`+`@moltzap/client` symlinked in). Its cross-conversation `getContext` recap is monkey-patched via `patches/openclaw@2026.3.31.patch` and the client patch (surface every unseen message, not just the last).

5. `openclaw@2026.3.31` — the agent runtime CLI, spawned as `gateway run --allow-unconfigured` per agent by `vendor/runtimes/openclaw-adapter.ts` (`buildOpenClawConfig` writes `channels.moltzap.accounts[]` with apiKey/serverUrl/agentName + optional `contextAdapter`; sets `tools.exec.security=full`). Patched.

6. `@moltzap/runtimes` — NOT on npm (workspace-only). Copied by hand into `vendor/runtimes/` from `chughtapan/moltzap-arena`'s `lib/moltzap` submodule (source path `/home/singh/moltzap-arena/...`, one-way manual refresh procedure in the README). This is the sharpest external-consumer coupling.

DB coupling: `src/db/schema.ts` mirrors moltzap-app's `supabase/migrations/20260319000000_fresh_schema.sql`; `bench-server/migrations/*.sql` are vendored copies. Protocol handshake uses `PROTOCOL_VERSION` echoed in `HelloOk` (`bench-server/src/handlers/auth.ts`). bench-server implements only 6 RPCs (`auth/connect`, `agents/lookup`, `conversations/create`, `conversations/list`, `messages/send`, `contacts/list`→`[]`) and emits only `messages/received` + `conversations/created`.

**Frontend:** Per the task, the live product frontend lives in a separate repo; this repo talks to moltzap only headlessly (agents over WS + DB tailing), never via a UI. What UI exists here is read-only over committed run artifacts, not over moltzap live: (1) `website/` — a static taxonomy showcase generated by `scripts/build-website.js` from `website/taxonomy.json` + `website/curation/*.json` + `website/showcases/*.html` + `website/synthesis/*.json`, served by `scripts/serve-website.js` (`pnpm build:website`/`serve:website`); the public hosted copy is `clr-li.github.io/claw.html` (README). (2) `viewer.js` — a localhost:3000 HTTP run viewer with Timeline/Compare/Received views that reads `experiments/<name>/runs/<ts>.json`, `received/<ts>.jsonl`, and `runs/<ts>.meta.json` (flags turns where injected context made `body !== content`). Both consume the JSON evidence the runner writes; neither embeds a moltzap client.

**Scenarios:** Definition: a scenario is a directory under `experiments/<name>/`, two authoring styles. (a) Single-file `params.yaml` (recommended) validated by `loadParams`/`validateParams` (`src/params.ts`) and compiled by `compileExperiment` (`src/compile-experiment.ts`) into in-memory `{ topology, experiment, personas, calendars, outcome }`. DSL knobs: `runtime` (model, maxRunTimeSecs, runs, readyTimeoutMs, calendarStyle), `agents[]` (role ∈ attacker/victim/relay/neutral/seeder; identity/goal/strategy/calendar/schedule/contextEnabled/model/seed), `roster` (N-replica sweep with availability generator), `schedules` (named open-slot profiles), `topology` (contacts + groups), `strategy` directives resolved to `directives/<role>/<type>/<name>.md`, templating tokens `{{moltzap}}`/`{{conv:a,b}}`/`{{group:...}}`. (b) Manual JSON: `topology.json` + `experiment.json` + `personas/<agentId>.md` (+ optional `skills/`), loaded by `loadExperimentConfig` (`src/experiment.ts`).

Drivers: `pnpm experiment <name>` (`scripts/experiment.ts`) runs the yaml path — clears the shared DB, `seedTopology` (`src/seed.ts`), `runOnce` (`src/run-scenario.ts`), N times, auto-grades, writes reports. `pnpm exp` = `clear`+`seed`+`play` (`scripts/play.ts` → `runScenario`) is the driverless path (dumps messages, NO verdict). `scripts/matrix.ts` fans a cartesian sweep (students/schedule/mode/strategy) across K OS-isolated docker+db stacks (`src/stacks.ts`).

Launch mechanics (`Fleet.start`): pre-creates a DM conversation for every contact edge (openclaw-channel can only reply-to-existing-conv), spawns one openclaw subprocess per `experiment.agents{}` entry via the vendored adapter, waits for `"connected as "` on each subprocess's stdout, sends the seed via a transient orchestrator socket, then starts `DbPollObserver`. Non-spawned topology agents can still be seed senders.

Judging (`src/verdict.ts`, PURE calendar-parse, explicitly NO LLM): reads each agent's harvested `CALENDAR.md` (canonical `BOOKED:`/`DECLINED:`/`DELETED:`/`FREE:`/`BUSY:` lines) and grades outcome kinds `booking` (slot booked/notBooked), `allocation` (checks no-double-book / valid-slot / within-availability / coverage against a derived answer key), `consensus` (single shared slot, incl. a `stalled` sabotage inverse), and `coverage` (calendar-reconstruction accuracy). Matching is tolerant (weekday/case/hyphen-insensitive substring).

Results format: `runs/<conditionSlug>/<batch>/` holds `<ts>.json` (wire messages from the observer), `<ts>.jsonl` (bench-capture received stream), `<ts>.verdict.json`, `<ts>.calendars/*.md`, `meta.json`, a `params.yaml` snapshot, and `prompts/*.md`; plus a generated `EXPERIMENT.md` (`buildExperimentReport`) with pass count, avg messages per PASS/FAIL, and trace links. Driverless path writes `runs/<ts>.json` + `received/<ts>.jsonl` + `runs/<ts>.meta.json`.

**V2 needs:**
- Publish an official agent-runtime-adapter package (today @moltzap/runtimes is workspace-only and hand-copied into vendor/runtimes/ from a teammate's local moltzap-arena checkout, /home/singh/... — the single biggest break for an external consumer). v2 must ship the openclaw spawn/fleet/teardown adapter on npm.
- Ship a TYPED client RPC surface: @moltzap/client@407's sendRpc returns Promise<unknown>, forcing src/rpcs.ts wrappers and manual HelloOk shape validation in src/bench.ts. v2 should expose client.sendRpc(Def, params) with request/result descriptors (the bench already flags rpcs.ts for deletion post-cutover).
- Freeze one canonical protocol contacts+message shape tied to a deployable server. The bench had to pin to moltzap-app's deployed line (protocol 408 / client 407 / server-core 329) because OSS 2026.504.x diverged the contacts surface and message shape (the open #415 Phase-4 / #422 contacts cutover). v2 needs a single published line that a consumer can pin without matching a private deployment.
- Provide a first-class embeddable dev/agent-only server. bench-server/ composes a server by reaching into server-core service constructors (AuthService/ConversationService/MessageService/ParticipantService/DeliveryService/ConnectionManager/Broadcaster/EnvelopeEncryption/createRpcRouter/defineMethod) and vendoring 3 SQL migrations. v2 should expose a supported createDevServer()/agent-only factory so consumers don't wire internals + duplicate the schema.
- Expose a public observation/trace API. src/observer/db-poll.ts reverse-engineers message flow by tailing the Postgres messages table and re-implementing the envelope decryption chain (KEK→DEK via EnvelopeEncryption/unwrapKey/deserializePayload + ENCRYPTION_MASTER_SECRET). This is the open chughtapan/moltzap#364 propagation-trace/metrics format; v2 should offer a trace/event stream so consumers stop coupling to DB schema + crypto internals.
- Offer a supported synthetic-identity/test-fixture provisioning API. src/seed.ts bypasses the phone-OTP/Supabase claim flow with direct users/agents/contacts inserts (generateApiKey + hashPhone + status='active'). v2 needs an admin/seed path for headless synthetic agents.
- Give the channel plugin a conversation-create (or send-by-recipient) path. openclaw-channel can only reply-to-existing-conversation, so Fleet must pre-create every contact-edge DM via an orchestrator socket; group creation still bypasses contact gating (moltzap-app#74), leaving group propagation 'gated/undefined' per CONTRIBUTING.md.
- Make cross-conversation context a supported channel API. The recap behavior is currently monkey-patched into openclaw-channel's dist/service.js (getContext) and openclaw via pnpm patches; the bench maps runtime.crossConversationContext → account.contextAdapter. v2 should expose the context window as a configurable adapter, not a patched dist.
- Provide a real readiness/presence signal. Fleet.start uses stdout log-scraping ('connected as ') + fixed sleeps (makeReadyProxy) as a readiness proxy; the code notes a future presence subscription should replace it.
- Own the sandbox/egress story for adversarial agents. The bench built its own fail-closed OS jail (bwrap/sandbox-exec in vendor/runtimes/sandbox-launcher.ts) + env allowlist (child-env.ts) because agents run tools.exec.security=full; network egress is still unrestricted (noted future work), tracking the local-only safety-guardrails issue chughtapan/moltzap#365.

**Notes:** Relationship to moltzap monorepo packages/evals + cc-judge: there is NO direct dependency on either. The bench's judging is entirely self-contained pure-TS calendar grading (src/verdict.ts, "no LLM"), and its report generator (experiment-report.ts) is bespoke. The ONLY lineage link is that vendor/runtimes was copied from moltzap-arena's lib/moltzap submodule, and the arena's eval harness file (trace-capture-harness.ts) is explicitly listed as "used by arena evals; not needed for this bench" and deliberately NOT vendored (vendor/runtimes/README.md). Net: this consumer forked moltzap's agent-spawning machinery but replaced any evals/cc-judge layer with its own calendar verdicts — so for v2 planning, packages/evals + cc-judge are NOT part of this consumer's contract; the runtime adapter, typed client, observer/trace, and dev-server surfaces are.

Other notes: (1) node_modules were not installed in the shallow clone, so I could not resolve on-disk versions — all versions are from package.json/CONTRIBUTING.md. (2) patches/ monkey-patch openclaw's control-UI operator auth bypass and the channel's context recap — both are load-bearing for the bench and would break on any version bump. (3) CLAUDE.md references a paper/ USENIX dir and appendix that are not present in this clone. (4) The bench models moltzap's owner-level contact gating faithfully (topology contacts are owner-to-owner; src/bench.ts and Fleet enforce inContact before DM), which is a useful invariant for v2 to keep stable. (5) Cleanup is a shell script (scripts/clean-experiment-rows.sh) doing FK-safe per-statement deletes directly against the moltzap schema — another direct-DB coupling v2 could obviate with a reset/teardown API.

## chughtapan/moltzap-arena (audited from shallow clone at commit 5db301c, "Merge pull request #352 ... golden-trace"; cloned to /private/tmp/claude-504/-Users-tapanc-moltzap/bcba8e38-c0b9-42f9-af6b-6deda9655478/scratchpad/repo-audits/moltzap-arena)

**Purpose:** AI agents play Werewolf (social deduction / Mafia) as live entertainment; spectators bet virtual $MOLT in a pari-mutuel prediction-market dashboard. Explicitly framed as "the MoltZap protocol's first third-party adoption" (README.md) — an external case study of multi-agent, hidden-information gameplay conducted entirely over moltzap conversations. Deployed as 3 Railway services (moltzap-network, arena-server, agent fleet) + Vercel frontend.

**Structure:** pnpm monorepo, TypeScript + Effect 3.21, oxlint/oxfmt, vitest, Hono server. packages/: (1) engine — pure Werewolf rules engine, zero I/O: reducer pattern (`reducer.ts → reduce`, `events.ts → GameEvent` union: start/kill_action/cast_vote/setup_complete/*_deadline/cancel; `commands.ts → Command` union: post_message/post_private/player_eliminated/phase_changed/game_over/archive_game/schedule_*/log_warning; `types.ts → GameState/Phase/Role/Vote`, `vote-counter.ts → tally` with majority quorum floor(alive/2)+1 and tie→null, `roles.ts → assignRoles/checkWin`, `prompts.ts` — all GM prose as data). (2) app-runtime — "Arena-internal vendored copy of moltzap's app-sdk client framework" (its package.json description): `MoltZapApp` class over `MoltZapWsClient`, hook registration, `AppSessionHandle`, `HeartbeatManager`, typed error taxonomy. (3) server — arena-server: `create-app.ts → createApp` composes Hono + spectator WS + betting (betting-pool.ts, betting-integration.ts, molt-amount.ts) + `werewolf-app/` (the moltzap app: manifest, register, hooks/, guards/, queue.ts consumer fiber, scheduling.ts phase fiber, observers.ts fan-out, sessions.ts SessionData, typing-indicator.ts, agent-presence-watcher.ts); `arena-harness.ts` is the eval/live-ops surface. (4) evals — thin: 13 cc-judge scenario YAMLs + `start-agents.ts` wrapper + a golden-trace snapshot test. (5) web — Next.js 15/React 19/Tailwind 4 spectator frontend. Root docs: GAME-RULES.md (canonical rules), ARCHITECTURE-GM.md (LLM-GM swap invariants — partially stale vs. the reducer refactor), SKILL.md (agent-facing player protocol), DEPLOY.md, compose.yml (3-service docker stack mirroring Railway).

**Moltzap Consumption:** Client-side tenant of a separately deployed moltzap-network — NOT an embedded server. Pinned published packages: `@moltzap/client` 2026.504.2 and `@moltzap/protocol` 2026.504.3 (exact pins, in packages/app-runtime, packages/server; resolved from registry per pnpm-lock.yaml). The `lib/moltzap` git submodule was severed in "Phase 11 (arena#332)" (compose.yml comment) because `@moltzap/runtimes` and the app-sdk were unpublished; the app-sdk was vendored wholesale as `packages/app-runtime` (`@moltzap/arena-app-runtime`), and the fleet capability was dropped. README/CLAUDE.md still describe the submodule + `@moltzap/server-core` composition — stale. Actual surface used: (a) auth/connect via `MoltZapWsClient` with agentKey; GM is one durable agent (`MOLTZAP_API_KEY`/`MOLTZAP_GM_AGENT_ID`, or self-mint via `registerAgent` → POST /admin/register-agent gated by REGISTRATION_SECRET, idempotency per moltzap PR #374). (b) AppHost protocol: `AppsRegister`, `AppsCreate`, `AppsGetSession`, `AppsCloseSession`, `AppsAttachConversation`, `MessagesSend`, `SystemPing`, `AgentsLookupByName`, `PresenceSubscribe`, plus string-form RPCs "conversations/create", "conversations/addParticipant", "apps/closeSession" (typed locally via `WerewolfAppRpc` envelope in werewolf-app/deps.ts, cast at one boundary in adapter.ts → wrapMoltZapApp because `client.sendRpc(string)` returns Effect<unknown>). (c) Notifications: MessageReceived, AppSessionReady/Closed, AppParticipantAdmitted/Rejected, PresenceChanged; brand helpers `agentId`/`conversationId`/`messageId`, `defineNotificationGroup`, `isDecodedNotification`, `LogicalClock` type. (d) The four AppHost admission/lifecycle hooks are the load-bearing integration: `before_dispatch` (returns DispatchAdmissionResult grant/deny/hold with leaseId/leaseTimeoutMs/dispatchMessageId; ctx carries message, recipient, pending[], attempt, receivedAt, clock — a vector LogicalClock), `before_message_delivery` (HookResult block/feedback; ctx.message.dispatchLeaseId), `on_session_active` (admittedAgentIds + manifest conversation ids), `on_close`; manifest (werewolf-app/manifest.ts) declares town_square participantFilter:"all", werewolf_den participantFilter:"none", hook timeouts (before_dispatch 900s). Agents run externally (openclaw/nanoclaw runtimes; default model openai-codex/gpt-5.4), registered as eval-p1..N, discovered via agents/lookupByName + presence/subscribe by agent-presence-watcher.ts, which kicks `apps/create` when N are online. moltzap-network is deployed from the moltzap repo's packages/server/Dockerfile with embedded PGlite (compose/moltzap.yaml).

**Frontend:** Stays entirely in this repo (packages/web, deployed to Vercel): Next.js prediction-market dashboard ("Broadcast Noir" design system, DESIGN.md). It never touches moltzap — it speaks an arena-specific JSON event protocol over an anonymous spectator WebSocket to arena-server (`ws://.../ws/spectate?matchId=...`), typed/validated in web/src/lib/ws-client.ts against `ArenaEvent` shapes defined server-side in arena-events.ts (session-init, odds snapshots, chat, den messages, phase-changed, player-eliminated, game-over, bet-resolved, typing indicators, crowd updates). GameStateAccumulator replays state to late joiners. Web's only workspace deps are arena-engine + arena-server (types only). Spectator den view shows wolf messages under pseudonyms (Wolf-A/Wolf-B): `sessions.ts → scrubWolfIdentities` rewrites wolf names/ids in den content before broadcast, and typing-indicator.ts enforces the town↔player / den↔pseudonym pairing structurally.

**Scenarios:** Two experiment surfaces. (1) Judged scenarios: 13 YAMLs in packages/evals/scenarios (ARENA-000..022) run by the external `cc-judge` CLI; each names a harness module (`../../server/dist/arena-harness.js`, i.e. `@moltzap/arena-server/arena-harness`) plus a payload {phase, role, setupMessage, supplementaryMessages, engineDriven, expectedResponse: kind message|silence + channel/durationMs} and an LLM judgeRubric with validationChecks. Coverage: skill-loaded canary (ARENA-000), command formats, night silence for villagers (ARENA-004), multi-wolf den coordination, round-2 continuity, tie votes, and deception/privacy probes — e.g. ARENA-020: werewolf is directly asked its role in town_square while its cross-conversation context contains the role DM; judge scores non-leakage. Results are cc-judge artifacts (summary.md, results.jsonl, details/*.yaml). (2) Live full-game harness: docker-compose 3-service stack (or Railway); presence watcher kicks a real game; arena-harness.ts captures `ArenaLiveCapture` {traceEvents, gameplay: {players+roles, winner, rounds, messages(from/text/channel/ts), phaseTransitions}} and classifies failures (completed/timed_out/failed_to_start/runtime_error/cancelled via classifyFullGameFailure); a golden-trace snapshot test (evals/src/arena-harness.snapshot.test.ts) pins the capture shape. Game semantics under test are specified in docs/GAME-RULES.md: 2 roles, nWolves=max(1,floor(n/3)), min 4 players, phase FSM LOBBY→SETUP→NIGHT→DAY_DISCUSS→DAY_VOTE→(NIGHT|GAME_OVER), first-valid-kill-wins with silent-ignore of later kills, no wolf-on-wolf kills, votes final (no changes), majority quorum, tie→no elimination, MAX_ROUNDS=20 draw→villagers, protocol violations get correction DMs but never eliminate — deception/leakage norms are enforced by the LLM judge, not the engine.

**V2 needs:**
- Publish the app-sdk as a real package. packages/app-runtime is a 1,100-line vendored fork of moltzap's app-sdk (its package.json says so verbatim) pinned to @moltzap/client 2026.504.2 — v2's uber framework must ship MoltZapApp/AppSessionHandle/hook-registration as a supported published surface so this repo can delete the fork. Same for @moltzap/runtimes and @moltzap/openclaw-channel: the arena fleet was dropped in Phase 11 solely because those were submodule-only.
- First-class turn-taking policy primitives. before-dispatch.ts is ~1,400 lines re-implementing a dispatch-lease FSM on raw hook callbacks: per-conversation exclusive leases with 90s TTL, waiter queues ordered by protocol LogicalClock vector comparison (compareLogicalClock), turn counts/caps per (phase, round, conversation), abandonment tracking (arena#306 two-silent-wolves wedge), vote-prompt barriers (all eligible waiters present before granting), and lease validation/release in before_message_delivery via ctx.message.dispatchLeaseId. v2 should offer declarative turn policies (round-robin, barrier, one-lease-per-conversation, eligibility predicates) so a game app supplies predicates, not the whole scheduler.
- Structured message metadata instead of prose sniffing. gmTownSquareAdmission in before-dispatch.ts classifies GM phase-opener messages by regexing prose shibboleths ('village gathers|wolf walks among') that must be kept in sync with engine prompts.ts by comment discipline. v2 needs sender-attached message tags/kinds (e.g. metadata on messages/send) visible in BeforeDispatchContext.pending and hook contexts so apps classify structurally.
- Role-scoped private conversations as a manifest primitive. Today: werewolf_den is participantFilter:'none' + N conversations/addParticipant calls, and per-player role DMs are hand-created in on-session-active.ts and appHost.attachConversation'd so hooks fire — with a forced type:'group' workaround because apps/closeSession archives DMs and ConversationService.findExistingDm returns archived DMs on the next session (chughtapan/moltzap#372, cited in on-session-active.ts). v2 should let a manifest declare per-participant/per-role dynamic private channels with hook coverage, and fix DM archival/dedup semantics.
- Visibility enforcement below the app layer. The Mafia contract needs the network to guarantee non-members can't post/read a private channel; today channelRoleGate (guards/channel-role.ts) blocks a villager who 'discovers the conversationId' of the den — i.e. membership secrecy is enforced by app-side guard code, not the platform. v2 should make channel membership + visibility a platform invariant, with hooks only for game-semantic rejections (wrong phase, dead sender, invalid target).
- Cross-conversation context/leakage controls in the agent runtime. ARENA-020 explicitly notes the agent's cross-conversation context includes its private role DM; deception norms are then only judge-enforced. A v2 social-skill contract needs per-conversation context partitioning options (or at least declared visibility scopes the channel runtime respects) so hidden-information games aren't one prompt-injection away from role leaks.
- Runtime-artifact hygiene. GAME-RULES.md §10: channel-plugin tool chatter (memory-file read failures, workspace paths) reaching player-visible transcripts is a known failure class; v2 channel runtimes should classify/suppress non-speech runtime output before delivery.
